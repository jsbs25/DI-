# 02 — 目标架构设计（Phase 2）

- **日期**：2026-11-12
- **依据**：阶段 1 审计（`server.ts` 单体、`store.ts` JSON+文件存储、`messengerWs.ts` 内存 WS、`discovery.db` node:sqlite、`desktop/` Electron、`server/calls` LiveKit 信令）+ 01 平台比较。
- **约束**：保留 React 前端、Express 业务逻辑与 API 契约、账号/好友/隐私/通知/Messenger/Electron；月费目标 0 USD（受免费额度限制）；不修改业务代码/数据（本阶段）。

## 方案 A：Cloudflare 全栈架构

### 拓扑
- **前端**：Cloudflare Pages（`vite build` 产物，SPA fallback）。
- **API**：Cloudflare Workers（按模块拆分路由/服务，逐步替代 Express）。
- **数据库**：D1（关系化迁移）+（可选）KV 缓存（非事实源）。
- **文件**：R2（私有桶 + 鉴权/签名读取，替代 `server_data/uploads`、`books` 静态化部分）。
- **实时**：Durable Objects + WebSocket（Messenger/Presence/通知推送）；消息事实落 D1。
- **通话**：信令经 Workers/DO；媒体 P2P WebRTC + STUN；TURN 受限（见 05）。
- **桌面端**：Electron 继续本地运行，通过 HTTPS/WSS 访问云端 API（与 Web 共用账号/数据）。

### 优点
- 同域/同生态集成度高，全球边缘分发，静态与 API 可统一在 Cloudflare 网络下管理。
- 理论上可在免费额度内覆盖“低流量初期”的 Pages+Workers+D1+R2+DO 组合（**额度需核实**）。

### 缺点与风险
- **迁移成本极高**：几乎全后端重写（Express→Workers、fs/sqlite→D1/R2、ws→DO、内存态→持久化/DO 状态、定时抓取→Cron/Queue 受限）。
- `discovery.db` 的 WAL/FTS5 与复杂查询需 PoC；`server_data.json` 语义与高频 `persist()` 需重建一致性模型。
- Messenger/通话/多端同步正确性风险高；免费额度（CPU/子请求/DO/D1 行读写）易成为瓶颈。

### 评估
| 维度 | 评价 |
|---|---|
| 免费程度 | 潜在高（若严格控量）**UNVERIFIED** |
| 迁移难度 | **极高** |
| 兼容性（现有代码/运行时） | **低** |
| 稳定性 | 取决于重构质量与配额 |
| 性能 | 边缘优势明显，但受 Worker/DO 限制 |
| 数据安全 | 可设计为强（私有 R2、D1 权限）但实现复杂 |
| 实时通信能力 | 可达成但工程量大 |
| 长期维护 | 两套心智（本地单体 vs 云原生）并存风险 |
| 潜在收费风险 | 配额超限、DO 使用增长 |

## 方案 B：Cloudflare 前端 + 独立 Node.js 后端（免费/低成本 PaaS）

### 拓扑
- **前端**：Cloudflare Pages（静态 SPA）。
- **API/WS**：保留 **Express + `tsx` + `ws` + 现有 store 逻辑** 为主，部署到支持 Node 常驻进程的托管平台（候选：Render/Koyeb/Fly.io 等免费层 **UNVERIFIED**）；反向代理提供 HTTPS/WSS。
- **数据库/文件**：短期可沿用“进程内加载 + 持久卷/对象存储”需视平台能力而定（多数免费 PaaS **无可靠持久盘**）；中期建议迁移到托管 DB（Turso/Neon/Supabase/D1 需经 API 层访问）与对象存储（R2/S3 兼容）。
- **实时**：继续使用现有 `/ws`（`messengerWs.ts`）与同进程状态；需解决单实例/休眠/扩展性。
- **桌面端**：指向同一后端域名；本地 dev 模式不变。

### 优点
- **最大程度保留现有后端代码与行为**（API、WS 协议、`store` 语义、`node:sqlite` discovery、本地文件逻辑可渐进改造）。
- 前端全球分发与 HTTPS 由 Pages 解决；后端改动面可控。

### 缺点与风险
- **“永久免费且常驻”后端难保证**：免费实例常见休眠/冷启动/资源回收，导致 WS 断连、实时与通话体验差。
- 持久化存储在免费 PaaS 上常受限；若仍依赖容器本地盘，**存在数据丢失风险**（必须外置 DB/对象存储）。
- 多实例扩展时内存 session/WS 连接表失效，需粘性会话或外部状态（增加复杂度）。

### 评估
| 维度 | 评价 |
|---|---|
| 免费程度 | 初期可能接近 0，但**可用性/常驻性风险高** **UNVERIFIED** |
| 迁移难度 | **低—中**（前后端分离与配置/存储外置） |
| 兼容性 | **高** |
| 稳定性 | 受免费实例策略影响大 |
| 性能 | 单区部署延迟较高；可配 CDN 缓存静态 |
| 数据安全 | 取决于 DB/对象存储选型与 TLS/鉴权 |
| 实时通信能力 | 短期最好（复用现有），但受休眠影响 |
| 长期维护 | 较低（贴近现状） |
| 潜在收费风险 | 升级常驻实例、流量与存储 |

## 方案 C：混合架构（按模块择优，渐进演进）— **推荐方向**

### 拓扑（分阶段目标态）
- **前端**：Cloudflare Pages（静态、SPA fallback、HTTPS、自定义域）。`PASS` 适配预期高。
- **后端（阶段性双轨）**：
  - **轨 1（保功能/保数据优先）**：将现有 Express 单体以**最小改动**容器化/部署到可运行 Node 的托管环境（首选可验证免费层的 PaaS 或用户自有/教育资源；若无可靠免费常驻则明确 **BLOCKED for “严格 0 USD 且 24/7”**），对外提供 `/api` 与 `/ws`；前端 Pages 通过 `https://api.<domain>` 访问。
  - **轨 2（云原生演进，按风险排序）**：逐模块将**无状态/轻状态 API** 迁移至 Workers；**文件**迁 R2；**关系事实数据**迁 D1 或 Turso（经 PoC 选型）；**实时**最终迁 DO（或保留单实例 WS 直至 DO 就绪）。
- **数据**：先设计并验证 **D1/Turso 映射与迁移工具链**（离线演练），再切流；任何时候保留 `server_data*` 原始备份。
- **实时/通话**：Messenger 与 Calls 优先保证协议兼容；信令可与 API 同域，媒体保持 WebRTC P2P+STUN。
- **桌面端**：始终可配置后端基址（dev 指向本地，prod 指向云端 API），**不改桌面核心流程**。

### 模块迁移优先级（建议）
1. **Pages 静态前端 + 域名/HTTPS**（不动后端逻辑）
2. **对象存储抽象**：上传/头像/书籍文件读写从 fs 抽象为存储接口（先适配 R2 或 S3 API）
3. **只读与低写 API 外置试点**（搜索代理、公开内容）— 可选
4. **认证/会话与核心数据层**迁移（最高风险，需完整回归）
5. **Messenger WS → DO**（或维持单实例后端直至可用）
6. **Discovery/FTS 与抓取任务**（受 CPU/存储限制，可能降级为离线/定时批处理）

### 评估
| 维度 | 评价 |
|---|---|
| 免费程度 | **可分阶段逼近 0 USD**；24/7 高可用实时后端在严格零费下 **UNVERIFIED/受限** |
| 迁移难度 | **中—高（但可控、可回滚）** |
| 兼容性 | **中高**（允许保留 Express 过渡） |
| 稳定性 | 通过“先 Pages、后增量后端”降低爆炸半径 |
| 性能 | 静态全球快；API 取决于后端落点 |
| 数据安全 | 可按阶段引入 R2 私有+托管 DB+审计 |
| 实时通信能力 | 过渡期复用现有；目标期 DO |
| 长期维护 | 需维护迁移边界与双轨期文档 |
| 潜在收费风险 | 可控（每引入一项服务即核实配额） |

## 综合比较矩阵

| 准则 | 方案 A 全栈 CF | 方案 B CF前端+独立Node | 方案 C 混合渐进 |
|---|---:|---:|---:|
| 免费程度（理论） | 4 | 3 | 4 |
| 迁移难度（越低越好） | 1 | 4 | 3 |
| 保留现有代码 | 1 | 5 | 4 |
| 保留现有数据 | 2 | 4 | 4 |
| 实时通信落地确定性 | 2 | 4 | 3 |
| 数据安全可设计性 | 4 | 3 | 4 |
| 长期维护 | 2 | 4 | 3 |
| 潜在收费/不可用风险控制 | 3 | 2 | 4 |
| **综合推荐度** | 2.4 | 3.6 | **3.9** |

> 评分为工程判断（1-5），非官方指标；额度相关仍 **UNVERIFIED**。

## 推荐结论（预告，详见 09/最终决策）
**推荐方案 C（混合渐进）**：先以 Pages 实现前端全球 HTTPS 交付，再以“保留 Express 业务内核”的过渡后端保障功能与数据完整性，并行完成 D1/Turso+R2 的映射与演练，最后按模块收敛到 Cloudflare 原生组件。该路径**最符合“保功能、保数据、可回滚、分阶段验证”**；对“严格 0 USD 且 24/7 实时后端”目标需在阶段 2/3 诚实验证可用免费常驻资源，无法保证时必须降级为可接受 SLA 并明确标注。
